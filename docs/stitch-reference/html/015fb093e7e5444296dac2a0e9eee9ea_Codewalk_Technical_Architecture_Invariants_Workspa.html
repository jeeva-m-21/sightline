Design Intent /

Isolation Rationale

Zero Mutability on Financial Records

Why isolate PaymentLedger from Orders? Mutating order status (e.g. PENDING → PAID → FULFILLED) requires row-level locking. Isolating financial entries into an append-only ledger eliminates lock contention on high-frequency transactions and satisfies SOC2 audit requirements via cryptographic hash validation.

Operational Entity: Order

Allows high concurrency updates to state machines, shipment references, and customer metadata without touching financial ledger locks.

Financial Entity: PaymentLedger

Strictly append-only. Compensating transactions record refunds or reversals without destructive updates to previous entries.

INVARIANT ·

Append-Only Financial Idempotency

When an Order transitions through state changes, prior financial ledger rows are never updated in-place. Compensating ledger transactions are created instead, preserving cryptographic chaining.

verified

Enforced at database schema level via PostgreSQL trigger constraints and ORM frozen immutability decorators. Prevents race conditions during webhook replay and asynchronous payment notification bursts.
